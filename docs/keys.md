## Worktree views

The panels aren't the only view. With a worktree selected, from any panel:

| Key | View |
|---|---|
| **`g`** | **Git diff.** Changed files down the left, the diff on the right, with a live fuzzy filter. On an open-PR row it shows that pull request's diff instead, fetched whole with `gh pr diff`. `Ctrl+r` marks a file reviewed ✓ and sinks it to the bottom — nebula-side bookkeeping only, no git state is touched — and every mark clears itself when HEAD moves or the file changes again, so what's left unticked is genuinely what you haven't read. `Ctrl+t` folds the file list into a directory tree and back — every directory open, a chain of directories that hold only each other shown as one row (`crates/nebula-tui/src`) — and the choice is remembered; in the tree `→`/`←` open and fold a directory, `Enter` or a click flips it, a directory's row lists what changed under it, and a directory wears the ✓ once every file under it has one. |
| **`f`** | **Find file.** Fuzzy finder over the worktree. `Enter` opens the file in an editor modal (vim by default; the `editor` setting or `NEBULA_EDITOR` picks another) — except a markdown file, which is read first: it opens as the rendered page in the file tabs below, where `Enter` is the editor and `m` shows the source — and `Ctrl+y` copies the path — ready to paste into an agent. The editor modal sits above every OVERLAY and is handed every key raw — vim owns `Esc` — so `Ctrl+q` is the only way out of it: one press kills the editor process and closes the modal, and the mouse is inert the whole time it is up. |
| **`F`** | **Find in files.** `git grep` into the same modal; `Enter` opens the hit at its line. |
| **`i`** | **GitHub issues.** The selected project's open issues, newest first down the left, the one under the cursor read on the right — number, title, author, labels, the description, and its comments once the cursor has rested on it for a moment (the `gh issue list` runs in the background once the cursor rests on the project, and again every couple of minutes while it stays selected, so the modal opens on rows already there; one `gh issue view` per issue you stop on). `j`/`k` walk the list, `PgUp`/`PgDn`, `Ctrl+d`/`Ctrl+u` and `Shift+↑`/`Shift+↓` read, `o` opens the issue in the browser, `r` asks GitHub again. `c` leaves a comment on the issue: a multi-row box (`Shift+Enter` for a newline) whose `Enter` posts the text as you with `gh issue comment` and lands back on the row, the pane saying the comment is on its way until GitHub answers and the conversation is read again; `Esc`, or an empty box, lands back without posting, and a post `gh` refused brings the box back with your text. `E` edits the issue itself, in place: the reading pane becomes a form on its title and description (`Tab`, `↑`/`↓` or a click move between the two, `Shift+Enter` breaks a line in the description), `Enter` sends both to GitHub as one `gh issue edit` and puts the pane back reading the new text, `Esc` drops the draft; a save GitHub refuses keeps the form up with `gh`'s reason on it and your text intact. `Enter` (or `p`) opens the QUICK PROMPT *for that issue* and `e` picks one of your AGENT PRESETS for it — the same box either way, titled `Quick prompt · issue #15 …`, with `Tab` / `Shift+Tab` / `Ctrl+N` working as they do in any quick prompt. What that launch starts is an ISSUE SESSION: the issue's URL travels with the create and reaches the harness as context on every spawn and resume — Claude and Pi in the appended system prompt, Codex and Cursor at the top of their first prompt — so the agent knows which issue the session is for before it reads a word of your task. Send the box empty and the task is `Fix GitHub issue #15: <title>`; `Ctrl+N` inside it cuts a fresh worktree named `issue-15-<title-slug>` instead of launching into the selected checkout. |
| **`v`** | **GitHub pull requests.** The selected project's open pull requests down the left — the OPEN PRS group's rows, newest first with the drafts below, drafts listed even while the panel hides them — the one under the cursor read on the right as the pane reads it: state, checks, branches, the description, then the conversation once the cursor has rested on it (the rows are the list the OPEN PRS beat already keeps warm, so the modal opens on them at once; one older than thirty seconds is re-asked underneath). `j`/`k` walk the list, `PgUp`/`PgDn`, `Ctrl+d`/`Ctrl+u` and `Shift+↑`/`Shift+↓` read, `r` asks GitHub again. `Enter` (or `p`) opens the QUICK PROMPT for a PR SESSION on that pull request, `e` launches one of your AGENT PRESETS on it and `n` picks a harness and starts one bare — the same launches the group row's `p`, `e` and `n` make, in the project's checkout of the PR's head branch. `c` (or `y`) comments on it and lands back on the row, `g` opens its diff, `o` opens it in the browser, `Esc`/`q`/`v` close. |
| *(none — an agent opens it)* | **File tabs.** What `nebula open <file>…` raises when a session runs it — ask an agent to "open it" or "show me the file"; it never opens one unasked, and only text files — an image or any other binary is refused at the CLI, so the agent names the path instead. A modal with a tab strip like the SETTINGS OVERLAY's, one tab per file: `←`/`→`, `Tab`/`⇧Tab` and `1`-`9` switch tabs, the focused tab's file is previewed underneath with the TREE BROWSER's highlighting — a markdown file as a rendered page (headings, lists, fenced code, tables, links; `m` flips it to the source and back, and the choice holds across tabs) — and `Enter` runs the editor in that pane (the tabs stay put; `:q` lands back on the strip with the file re-read). `↓`/`j` from the strip drops into the preview, where `j`/`k`, `Ctrl+d`/`Ctrl+u`, `PgUp`/`PgDn` and `Home`/`End` scroll and `↑` off the top returns to the strip. This is the one OVERLAY where `Ctrl+q` is staged: from the editor or the preview it steps back to the tab strip, and only from the strip does it close; `Esc` backs out the same way. |
| **`b`** | **File tree browser.** Tree on the left, syntax-highlighted preview on the right (a markdown file as a rendered page; `Ctrl+r` flips it to the source and back), and an always-live filter that narrows the tree to matching files and the directories holding them. `→` expands a directory and `←` collapses it; `Enter` folds or unfolds a directory, and on a file it loads the file into the *preview pane* rather than the floating editor modal that `f` and `F` open — the tree stays where it is. The preview takes the DIFF VIEWER's scroll keys: `Ctrl+d`/`Ctrl+u` half pages (`Ctrl+u` only while the filter is empty — with text typed it is the LINE EDITOR's kill-to-start), `Shift+↑`/`Shift+↓` a line, `PgUp`/`PgDn` a page, `Home`/`End` the ends. `Ctrl+y` copies the selected path, and dragging the tree/preview border resizes the tree side. |

## Full keymap

| Context | Key | Action |
|---|---|---|
| Panels | `Tab`/`Shift+Tab` (or `Ctrl+Shift+L`/`Ctrl+Shift+H`), `h`/`l` or `←`/`→`, `j`/`k` or `↑`/`↓` | move FOCUS / selection through visible panels; the walk stops at both ends (`Tab` at the TERMINAL PANE, `Shift+Tab` at the WORKSPACES BAR while it is shown and at the first visible panel when it is hidden) instead of cycling, and landing on a live pane takes its input; `h`/`l` stop one short of each end, and a double tap there (`l`,`l` at Sessions, `h`,`h` at the first visible panel) jumps the boundary; so do `k`,`k` on a panel's first row (up into the WORKSPACES BAR) and `j`,`j` in the bar (back down to the panel you came from). The double taps are the letter keys' way over that boundary, but `Shift+Tab` needs no double tap — it steps into the WORKSPACES BAR in one press. `Ctrl+Shift+L`/`Ctrl+Shift+H` are the same two walk actions and need the KITTY PROTOCOL to arrive at all, so Ghostty and kitty get them and Terminal.app never will |
| Panels | `Ctrl+→` | cross into the terminal pane *without* taking its input (`Tab`, or a double tap of `l`/`→` at Sessions, takes it) |
| Panels | `Enter` | drill in; on a session: attach |
| Any panel | `/` | fuzzy jump across every workspace, project, worktree and session — in *every* workspace (`Ctrl+n/p` move, `Ctrl+o` opens the hit, `Ctrl+f` just lands the selection on it). The list is nested: each project is a bold header with its rows stepped in under it by name alone — a session by its title, a dim `23m ago` pinned right — and a project from another workspace names it on the right (`◇ client`). Until you type it is a recent overview, project by project: only the projects and their sessions, in attention order — the project with a session waiting on you first, and inside each project the sessions waiting on you, then running ones, then unread finishes, then the rest by last interaction — with the cursor on the top session, so `/` `Enter` is the fastest way back to what needs you or to what you last ran. `Enter` on a session that NEEDS FEEDBACK — the red row — attaches and focuses the TERMINAL PANE whatever `palette_enter_attaches` says, since the only thing to do with a jump to a question is answer it; `Ctrl+f` is still the way to only land on it. Typing searches every row, workspaces and worktrees too, still grouped under their projects; the query runs over each row's full `workspace/project/branch/session` path, so a project's, branch's or workspace's name narrows to what is under it, and a project header the query only brought along to hold its rows is left out of the `(hits/total)` count. Every open pull request nebula has listed is a row too, `↗ #42 title` under its project, searchable by number or title (`#` lists them all), and badged `draft` or `ready for review` after the title — the same states the sidebar's PR rows wear, spelled out here where there is room (`ready for review` is an open pull request that is not a draft; it says nothing about approvals, checks or mergeability), or `merge conflicts` / `checks failing` in red, the row red with it, when GitHub says the pull request cannot merge as it stands — so a draft is told from a finished one, and a blocked one from either, before it is picked, by the word and not only by its color; the badge follows the next `gh pr list` answer, so a draft marked ready flips under an open palette. `Enter` on one selects its project (switching workspace if need be), unfolds the OPEN PRS group and lands the WORKTREES cursor on the row, so the PR PREVIEW reads it in the pane — no checkout or session of its own needed. `Ctrl+o` on it is the explicit way out to the browser, as is `Enter` on the row once landed |
| Any panel | `]` / `[` | next / previous session in that same attention order, with no modal: one press lands on the next session waiting on you (then the running ones, then the unread finishes, then the rest by last interaction), wrapping at both ends. It is `/` `Enter` without the typing — a session in another workspace switches you there and selects its project, worktree and row, and `palette_enter_attaches` decides whether the pane is attached and focused or only selected and previewed — a session that NEEDS FEEDBACK is attached and focused either way, as it is under `/` `Enter`. Landing on an UNSEEN finish reads it, so the DONE BADGE counts down as you cycle. With nothing red or blue it still walks the running sessions, then everything else; with no sessions anywhere the footer says so |
| Projects | `n` / `d` | add project / remove from list |
| Any panel | `o` | add ("open") a project — same prompt as `n`, from any focus |
| Add project | type + `Tab`, `↓↑` / `→` / `←` | browse for the repo: type to filter (bash-style Tab completion), arrows pick a directory, `→` steps in, `←` steps up, `Enter` adds the highlighted (or typed) path; `●` marks git repos |
| Projects | `r` | rename the row — a label, not a move: the folder on disk keeps its name and hangs off a `└` under the new one. A terminal cell has one font size (Kitty's OSC 66 renders half-size text, but WezTerm and Ghostty don't implement it), so the hierarchy is weight, opacity and position instead: the name you chose is bold, the folder is the dimmest theme color plus the faint attribute. An empty name puts the row back on the folder's name |
| Worktrees (checkout row) | `n` / `d` | new worktree / delete (typed confirm — deletes files) |
| Any panel, on the ⌂ root | `c` | the BRANCH SWITCHER: move the project's ROOT WORKTREE onto another branch — the selected checkout from the Worktrees and Sessions panels (a linked worktree's row only says why not: a worktree stays on the branch it was cut for), the project's root from the Projects panel and the Workspaces bar. It lists the current branch first, then the other local branches newest commit first, then the remote branches no local branch shadows, newest first — each with its last commit's subject and age — and `Enter` switches (a remote branch becomes a local branch tracking it). Type to filter, fuzzily, as in `/`; `↑`/`↓` or `Ctrl+n`/`Ctrl+p` move. Opening it starts one background `git fetch --all` (at most once a minute per checkout; `Ctrl+r` fetches again now) and the list follows when it lands. With nothing matching, `Enter` creates the typed branch off the current one and switches to it, changes and all (a name that starts with a remote's, like `origin/x`, is refused — it would shadow the remote branch). A checkout with uncommitted changes stops and asks how they travel: `s` stashes them under an entry named `nebula: <from> before switching to <to>` (if git refuses the switch, or stops part-way — a missing git-lfs does that — the files it wrote are undone and that entry is applied straight back), `b` brings them along (git's own switch, refused when they collide with the target), `c` commits everything first — untracked files too — after asking for the message (refused on a detached HEAD, where the commit would belong to no branch), and `d` discards changes to tracked files on a second `d`, unstaging first so untracked and newly added files stay; if the changes moved since the prompt opened — a new change, or another edit to a file already listed — it asks again. `Esc` backs out one step at a time. Nothing switches mid-merge, mid-rebase or with unresolved conflicts, and a git repository nested in the checkout (a `.claude/worktrees/…` checkout) is neither counted as a change nor committed. A branch another worktree has checked out is listed but refused, since git keeps a branch in one checkout. One switch runs per checkout: `Esc` while git works hides the modal and `c` brings it back, and an answer that lands while it is hidden is said in the footer. A switch that stops part-way puts back only files byte-identical to the target branch's, so nothing anyone wrote is touched; whatever it could not undo, it names. Sessions running in the checkout keep running and see its files change. The root row's right-click menu has it as **Switch branch…**; rebindable as `switch_branch` |
| Worktrees (checkout row) | `r` | run the project: starts the project's RUN COMMAND — **Run command** on the SETTINGS OVERLAY's Project tab (`s`) when it is set, else the `run` command from the checkout's `.nebula.json` (the PROJECT FILE, see [Configuration](configuration.md#the-project-file-nebulajson)) — in a RUN TERMINAL the DAEMON holds, so it keeps serving after the TUI quits. While the process lives the row wears a green `▶ running` — a bare `▶` when the word would cut the branch — and its output is the `▶ run` row in the Sessions panel, the command beside it. `r` again stops it: the whole process tree is killed and the row goes. A run that ends on its own leaves its row dimmed, and attaching it replays how it ended rather than running it again — only `r` starts one. Neither the setting nor a `.nebula.json` with a `run`, and the footer names both places. Nothing on this panel is renamed, so this is what `r` (the `rename` action) means here; the context menu has **Run** / **Stop run** too |
| Any panel | `Shift+Enter` / `Shift+O` / `Alt+Enter` | open the selected worktree: fires its OPEN COMMAND once — **Open command** on the SETTINGS OVERLAY's Project tab (`s`) when it is set, else the `open` command from the checkout's `.nebula.json` — `open http://localhost:3000`, say — through `$SHELL -c` in that checkout, from the TUI, so it opens things on the machine you are sitting at; its output is discarded. Neither set, and the footer names both places. The worktree is the one under the Worktrees cursor, from whichever panel you press it (a PROJECT OPEN PRS row has no checkout to open). `Shift+Enter` needs the KITTY PROTOCOL to arrive as a key of its own: Ghostty and kitty send it; Terminal.app sends a plain `Enter`, which drills into Sessions instead, and tmux flattens a shifted Enter to a plain one on its way to the pane whatever `extended-keys` says. So two keys are bound beside it: `Shift+O`, which every terminal delivers, and `Alt+Enter` — the `ESC` `CR` that Claude Code's `/terminal-setup` makes VS Code's terminal send for Shift+Enter, and that Option+Enter sends on a Mac whose terminal treats Option as Meta — which tmux passes through untouched. Terminal.app can be taught the real key instead: Settings → Profiles → Keyboard, add `⇧↩` with the action *Send Text* and the text `\033[13;2u`. The Worktrees context menu (`m`) has **Open** too |
| Worktrees (checkout row) | `p` | quick prompt into a fresh worktree: cuts a random branch off the fetched `origin/HEAD` (or the **Worktree base branch** setting) and starts the agent there, whatever checkout the cursor is on — the box opens with its frame green and a `NEW WORKTREE` chip naming the branch, and `Ctrl+N` inside it flips back into the checkout under the cursor. The full box is described under `p` below |
| Worktrees (PROJECT OPEN PRS row) | `p` | quick prompt as a PR SESSION on that pull request: the same box, titled `Quick prompt · PR #42`, its target row naming the PR and its head branch, and what you type is the first prompt. `Enter` starts the agent in the project's worktree on that branch — reused when one is already checked out on it, cut by the daemon otherwise — with the PR link and its work rule in the system prompt, and the checkout's row is up under the pull request the moment you press `Enter`, marked `creating` until the daemon's row takes its place. A fork's pull request gets a checkout named for the fork — `givemeurhats/main`, never your own `main` — so a contributor's PR from their `main` cuts its own worktree instead of landing in the root checkout. `Tab` / `Shift+Tab` in the box swap the harness or add a preset and keep the PR; `Ctrl+N` is refused, the checkout being the PR's own. A create the daemon refuses (offline, a fork since deleted) takes the `creating` row down and brings the box back with your text. `e` (below) is the same launch through the preset picker. The pull request stays what `p` and `e` are for while its row is selected, whichever panel has focus |
| Worktrees (PROJECT OPEN PRS row) | `n`; `m` / right-click | new SESSION scoped to that PR, on any enabled harness (the same rows as the NEW SESSION PICKER), in a checkout of the PR's head branch — reused when the project has one, cut by the daemon otherwise — which lists directly under the PR's row, stepped in behind a `└`, rather than among the plain checkouts above the group; `y` opens the COMMENT BOX on it (below); the context menu also opens the PR, its diff or that box |
| Worktrees (PROJECT OPEN PRS row) | `e` | agent preset on that PR: pick one of your saved AGENT PRESETS (below, under Sessions `e`) and it launches as a PR SESSION on the pull request. The picker hands the quick prompt box back with the preset applied — titled `Quick prompt · PR #42 · reviewer`, its target row naming the PR and its head branch — and `Enter` starts the agent in the project's worktree on that branch, reused when one is already checked out on it and cut by the daemon otherwise, with the PR link and its work rule in the system prompt (a Codex / Cursor cold spawn opens with it) and the preset's prefix + your task + postfix as the first prompt. Sent empty, the prefix and postfix go alone; a preset whose **Task** row is `skip` launches straight from the picker. `Tab` / `Shift+Tab` in the box still swap the harness or the preset and keep the PR; `Ctrl+N` is refused, the checkout being the PR's own. `Esc` in the picker closes it — no box was up, so none comes back |
| Worktrees (`OPEN PRS` header) | click; `↓` off the last checkout | fold the group down to its one-line header or open it back up — the triangle says which: `▾ OPEN PRS · 12` over the rows, `▸ OPEN PRS · 12` with them folded away. **Show/hide open PRs** in the panel's right-click menu does the same. Folded, `↑/↓` stop at the last checkout, a cursor that was on a pull request lands there with that checkout's session back in the pane, a checkout that sat under its pull request rejoins the plain rows (the cursor following it), and the fold survives a restart like `A`'s. Stepping `↓` off the last checkout into a folded group opens it onto its first pull request, so the fold never has to be undone by hand to walk the list. **Hide draft PRs** / **Show draft PRs** in the same menu flips the `hide_draft_prs` setting (Settings → Appearance): drafts leave the group and `/`, and the header counts `9/12` — listed over open |
| Worktrees (PROJECT ISSUES row) | `Enter` / double-click; `p`; `e`; `m` / right-click | the `ISSUES` group under the pull requests lists the project's open issues — the ISSUES MODAL's rows, `↗ #15 title` in green — and the pane reads the one the cursor rests on: description at once, the comments once they land, `PgUp`/`PgDn`, `Home`/`End` and the wheel scrolling it, the Sessions column folded to its rule meanwhile. `Enter` opens it in the browser, `p` is the modal's `Enter` for it — the QUICK PROMPT carrying the issue, into the project's root checkout — `e` launches an AGENT PRESET on it, and the menu offers the browser |
| Worktrees (`ISSUES` header) | click; `↓` off the row above it | fold the group down to `▸ ISSUES · 12` or open it back up (`▾ ISSUES · 12` over the rows); **Show/hide issues** in the panel's right-click menu does the same. Folding away the row the cursor is on lands it on the row above the header — the last pull request, or the last checkout with its session back in the pane. Stepping `↓` off that row into a folded group opens it onto its first issue (a folded OPEN PRS group opens first, on its own step). Remembered across restarts |
| Worktrees (any row) | `Ctrl+d` / `Ctrl+u` | half a panel down / up: the cursor jumps by half the rows the column has room for — checkouts and open pull requests alike — stopping at the first and last row, and the list scrolls after it so the row landed on is in view; `Ctrl+d` off the last checkout opens a folded `OPEN PRS` group the way `↓` does. The Sessions panel takes the same two chords (below); in a LOCKED PANE they stay the shell's EOF and kill-to-start, every LINE EDITOR keeps `Ctrl+u`, and the Projects panel leaves them unbound. Rebindable as `half_page_down` / `half_page_up` in Settings → Hotkeys |
| Any panel | `Shift+R` | refresh the pull requests now: the project's OPEN PRS list, the selected worktree's own PR ROW, and the description and conversation of the pull request the pane is reading are all asked of `gh` again at once — past the 15-second beat and the few-second floor a focus event respects — with the reader's scroll kept. `refreshing pull requests…` in the footer says it was heard; the rows repaint as the answers land. Its own key, not a meaning `r` takes on: it acts on the selected project and worktree, which every panel has, so it works from any row — `r` stays rename / edit everywhere but a checkout in the Worktrees panel, where it runs the project |
| Worktrees (PROJECT OPEN PRS row) / Sessions (PR ROW) | `y`; **Comment…** in `m` / right-click | comment on the pull request without leaving nebula: the COMMENT BOX is the same multi-row box `p` opens, titled with the row (`Comment on #42 …`). Type markdown as you would on GitHub, `Shift+Enter` or `^J` breaks a line, `Enter` posts it as you through `gh pr comment`, and `Esc` — or `Enter` on an empty box — cancels. `posting a comment on #42…` in the footer while `gh` runs, `comment posted on #42` when it lands, and the pane re-reads the conversation with your scroll kept, so the comment shows up under the ones it answers. A post `gh` refused — not logged in, no network, no `gh` at all — is flashed in `gh`'s own words and the box comes back with your text; if another modal was up when the refusal landed, the next `y` on that pull request starts from the text instead. Off a pull request row the key only says what it wants. Rebindable like every hotkey (`comment_pull_request`) |
| Any panel | `i` | GitHub issues: the ISSUES MODAL for the selected project (above) — read an issue, `Enter`/`p` prompts an agent on it, `e` launches an AGENT PRESET on it, `c` leaves a comment on it, `E` edits its title and description, `o` opens it in the browser, `r` refreshes |
| Any panel | `v` | GitHub pull requests: the PULL REQUESTS MODAL for the selected project (above) — read a pull request, `Enter`/`p` prompts a PR SESSION on it, `e` launches an AGENT PRESET on it, `n` picks a harness, `c` comments, `g` opens its diff, `o` opens it in the browser, `r` refreshes |
| New worktree | type a sentence, or `Enter` on the empty prompt | the branch name is slugified (`fix login redirect` → `fix-login-redirect`); empty takes a random `<adj>-<noun>-<verb>`. The branch starts at the freshly fetched `origin/HEAD` (normally `origin/main`), untracked — never at the root checkout's HEAD; with no `origin`, or a fetch that fails, it falls back to HEAD. **Worktree base branch** (Settings → General; `worktree_base_branch` in CONFIG.JSON) names another start — `master`, `develop` — resolved the same way: origin's fetched copy first, the local branch of that name otherwise, and `origin/HEAD` again in a repo that has neither |
| Sessions | `n` | new session: pick the harness (`→` drills into its model and effort, `Enter` takes your defaults) and it starts — no name or task box follows. The launch drops you into its pane, you type the agent's first prompt in the CLI, and the session titles itself from it. To start an agent on a task typed up front, use `p` (below). A shell terminal is `t` |
| Sessions (any row) | `Ctrl+d` / `Ctrl+u` | half a panel down / up, the Worktrees rule on this column: the cursor jumps by half the pill rows the column has room for — live sessions, terminals, the PR ROW and the `ARCHIVED` group's rows as one list — stopping at the first and last row, with the list scrolling after it so the row landed on is in view and the pane previewing what it lands on. The jump is sized by pills, so RECENT PROMPTS lines under live rows are not billed: over them it moves a little more than half a panel, over the archived rows it is for exactly half. Same rebindable actions, `half_page_down` / `half_page_up` |
| New session picker (Claude) | `Tab` | toggle Claude Cloud; `Enter` then opens Cloud's own wrapped task prompt (`Shift+Enter` or `Ctrl+J` inserts a line) — the one picker row that asks before it launches, a cloud session being nothing without its task |
| New session picker (any row) | `?` or `s` | open Settings → Agents parked on the highlighted harness's section, where its Enabled switch and default model and effort live (`s` types in the model/effort submenus instead, where the filter owns letters) |
| Sessions (cloud row) | `Enter`, `m` | `Enter` — or a click on the link in the CLOUD SESSION PANEL — opens the session's page in the browser; the `m` menu offers **Open in browser** and **Send to cloud session**, which queues a message on it. No **Attach** or **Restart**: the agent runs in the cloud, not in a terminal here |
| Sessions (agent row) | `Space` | **follow-up prompt, in the card itself.** The selected session's card expands in place into a small box — no modal over the screen — and what you type there goes to the agent already running in that session as its next turn: `Enter` sends it and folds the card back up, `Shift+Enter` / `Option+Enter` / `Ctrl+J` break a line, `Esc` folds without sending. Every card below it in the column moves down by what the box took, and off the bottom if the column runs out — the column scrolls to keep the box you are typing into on screen. While the box is open it owns the keyboard, so the panel's own letters (`a`, `d`, `r`…) are just letters; `Tab` still walks to the next panel and leaves the card expanded behind it. Each card carries the toggle it answers to: a `▸` at the end of its name row that a click expands, and a `▾` that a click folds — the same thing the `m` menu's **Follow-up prompt** row does. ## Chips and readouts

Two strips report state without being asked. The TERMINAL PANE's header shows one chip at a
time — the first of these that applies, so a scrolled-back exited session reads `exited`:

| Chip | What it is telling you |
|---|---|
| `exited` (red) | the session's process is gone. Keys stop reaching it — `Esc`, `Enter` and `q` leave the lock and everything else falls through to panel navigation — and the next attach is what respawns it |
| `scroll N` (yellow) | you are N lines back in the scrollback rather than at the live edge. Typing anything, or scrolling back down to the bottom, clears it |
| `starting…` (dim) | nothing has come off the PTY yet: the session was reaped while you were elsewhere and its CLI is booting now. The blank grid on its own reads as a hang, so the chip says otherwise |
| `INPUT` (accent) | the pane is locked and every key is going to the PTY — where `Enter`, the forward walk, a double tap of `l`/`→` and `z` all leave you |

The FOOTER carries the rest, left to right:

| Readout | What it is telling you |
|---|---|
| `nebula vX.Y.Z` at the far left | which nebula this is — the same string `nebula --version` prints, and the one thing on the bar that never moves with the cursor. It costs the key hints ~18 columns and steps aside only for a flash message that would not otherwise fit |
| `⇡ v0.22.0` right after it, in the warning color | a newer nebula is published on GitHub — the nudge to run `nebula upgrade`. Checked once at start and hourly after with one `curl` to the release page's redirect (no `gh` token, no API quota); it says nothing while it can't ask, and `NEBULA_UPDATE_CHECK_SECS=0` turns the check off |
| `◇ workspace` beside it | the open workspace everything else on screen is scoped to; click it for the workspace switcher (`w`) |
| `+3 files` after the breadcrumb | the selected worktree's dirty-file count, in the warning color. It rides the breadcrumb because it is context about that checkout, not chrome, and it is absent at zero |
| `✗ disconnected` | this client has lost the DAEMON. It is the client-to-daemon link and nothing else — a session's own health is its `●` STATUS DOT, and a hollow `○` is an agent the daemon restarted out from under. A healthy connection says nothing at all: the bar reports the link only when something is wrong |
| `2 agents · 1 term · 3 warm · 412 MB` at the right edge | live counts and nebula's whole memory footprint — this TUI, the DAEMON and every session's process subtree summed — re-read every 5 seconds while no modal is up. | `j - Move down` on the blank row above the bar, far left | the KEY COMBO DISPLAY (Settings → Experimental, `show_key_combos`), off by default: the key you just pressed in a keycap and what it did, for anyone watching a screen share — vim's `showcmd`. ## Mouse

The mouse is another way to press the keys, never a second set of behaviors: a click on a row is
the arrow keys landing there, a click on a row of a picking list (a menu, the `/` palette, the file
finder, the agent presets, the ssh hosts) is `Enter` on that row, a second click on a row you are
already on — a session, a checkout, a pull request, a settings row — is `Enter` on it, a right-click
is a click followed by `m`, and a click into the terminal pane is `Enter` on the pane. So a markdown
file clicked in the file finder opens read-first in the file tabs as `Enter` opens it, a preset clicked
in a pull request's preset picker starts the PR SESSION `Enter` starts, and a right-click on another
checkout brings its session into the pane as `↑/↓` onto it would. Double-click in the terminal selects
a word, `⌥`-click opens the URL or `file:line` under the cursor (browser / editor modal; a `.md` opens
read-first in the file tabs, `Enter` there for the editor), and dragging a
visible panel border resizes it. Hidden panels keep their last width for the next time they are shown.
A click on a project or worktree row (like `↑/↓` onto it) brings back the session it was last on, or
its top row — the most recently interacted session — when nothing is remembered yet or that session
is gone; only a worktree with nothing to show blanks the pane.
A click outside any modal (help, settings, a confirm, a prompt, the pickers) dismisses it, and
focuses the panel it landed on — only focuses it: the click was spent closing the modal, so it moves
no cursor, previews no session and switches no workspace. Landing in the terminal pane takes the
input lock the way a click there always does. That is not always the same thing as `Esc`:
the DIFF VIEWER, the PALETTE, the FILE FINDER, its grep view, the TREE BROWSER and the BRANCH SWITCHER all stage `Esc` —
the first press clears the typed filter and only a second one closes — where a click outside closes
them outright, first press. The CONTEXT MENU splits the same way: `Esc` backs out one submenu level
at a time, a click outside takes the whole menu. The rest (a CONFIRM DIALOG, a prompt, the agent
presets list, the preset editor) really do run their own `Esc`, side effects and landing included.
The wheel scrolls whatever the pointer is over: the WORKTREES PANEL and SESSIONS PANEL move their
lists without touching the selection, and the PR PREVIEW scrolls three lines a notch while a cursor
is resting on a pull request. Text selection: hold `Shift` while dragging (mouse capture bypass —
same as tmux).

A program that asked for the mouse itself — Claude Code's fullscreen renderer, vim with `mouse=a`,
htop, tmux with its mouse on — gets the left button the way a plain terminal hands it over: the
press, the drag and the release all reach it, and its own selection does the copying. Claude Code's
knows that its `/diff` panel sits beside the conversation; a screen-row copy of nebula's took the
panel along with the reply. nebula's own drag-select is for everything that never asked — a shell,
Claude Code's classic renderer — and `Shift`-drag selects through the terminal either way. A copy
the program sends its terminal as an OSC 52 write (Claude Code over `nebula ssh`, vim's OSC 52
clipboard, tmux with `set-clipboard` on) is passed on to the terminal you are sitting at, the route
nebula's own copy takes on a remote host.

A drag-select ends when the button comes up and not before: the wheel, the agent printing on, a
resize, even a replay that rebuilds the screen all leave a drag in progress where it is, since the
selection is pinned to the text rather than to screen rows. Drag past the pane's top or bottom edge
— onto the rule above it or the footer below — and the history scrolls under the pointer until it
comes back inside, a line per tick for each row past the edge, so a copy can run longer than the
pane is tall; the release copies every row the drag crossed, on screen or not.

A host terminal can forget that it was asked for the mouse — iTerm2's Session ▸ Reset (`⌘R`) does,
and so does a stray full reset — after which every click goes to the terminal and the wheel scrolls
its own scrollback instead of the pane. nebula asks for the mouse (and bracketed paste, focus reports
and the kitty keyboard flags) again every two seconds — never in the middle of a drag — so the mouse
comes back on its own; resizing the window also re-enters the alternate screen and repaints every cell.
