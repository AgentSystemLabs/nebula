Nebula — Client ↔ Daemon Interaction

How the TUI (and one-shot CLI commands) talk to the background DAEMON over the DAEMON SOCKET, plus the separate HOOK RECEIVER path agents use for status.

1. Process model

Same binary, two roles. Quitting the TUI does not kill sessions — the DAEMON owns every PTY.

2. Connect & handshake

On launch the client connects to the socket. If nothing listens, it auto-spawns nebula daemon with DAEMON SETSID (new session, no controlling tty). Then it runs the HANDSHAKE and checks PROTOCOL VERSION. 

sequenceDiagram
  autonumber
  participant C as Client (TUI / CLI)
  participant S as DAEMON (server.rs)
  participant R as Registry + SQLite

  C->>S: UnixStream connect (daemon.sock)
  alt socket missing / refused
    C->>C: spawn_daemon() — setsid + nebula daemon
    C->>S: poll connect (up to 3s)
  end

  C->>S: ClientRequest::Hello { protocol_version }
  alt versions match
    S-->>C: ServerEvent::HelloOk { daemon_pid }
  else VERSION SKEW
    S-->>C: ServerEvent::Incompatible
    C-->>C: bail with fix hint (make install vs nebula kill)
  end

  Note over C,S: TUI only — split socket into reader/writer tasks (IpcChannels)

  C->>S: ClientRequest::Subscribe
  S->>R: snapshot()
  S-->>C: ServerEvent::Snapshot (full tree + ui_state)
  S-->>C: stream ServerEvents via broadcast (deltas forever)

  Note over C: Client pins workspace scope at first Subscribe

3. Request / event planes

CLIENT REQUESTs go client → daemon. SERVER EVENTs push daemon → client(s). RPC-style CRUD replies with Ack / Error matching req_id; PTY traffic is session-scoped.

  • Subscribe → one Snapshot, then a broadcast fan-out of entity/status deltas to every connected TUI.
  • OpenWorkspace scopes this connection only — two TUIs can view different workspaces.
  • One-shot CLIs send a single request (e.g. AutoRenameAgent) and exit; no Subscribe.

4. Attach path (terminal pane)

When you drill into a SESSION, the TUI sends ATTACH. The DAEMON replays the scrollback ring, then streams live bytes. Keystrokes go back as Input. Detach never kills the child. 

sequenceDiagram
  autonumber
  participant TUI
  participant S as DAEMON server
  participant P as PTY SESSION
  participant A as Agent CLI

  TUI->>S: Attach { session, from_seq, cols, rows }
  S->>P: ensure_session (spawn/resume if dead)
  S-->>TUI: Scrollback { base_seq, data }
  Note over TUI: reset vt100 parser, apply replay

  S->>S: spawn forward task (subscribe PTY events)
  loop live session
    A->>P: stdout/stderr bytes
    P->>S: coalesced Output { seq, data }
    S-->>TUI: Output (attached clients only)
    TUI->>S: Input { data } (keystrokes / paste)
    S->>P: write to PTY master
    TUI->>S: Resize { cols, rows }
    S->>P: resize PTY
  end

  opt user focuses finished agent
    TUI->>S: MarkAgentSeen
    S-->>TUI: StatusChanged (unseen cleared)
  end

  TUI->>S: Detach
  Note over P,A: PTY + agent keep running

5. Status path (hooks — not over the socket)

Agent status dots are driven by the HOOK RECEIVER, a loopback HTTP server the DAEMON starts at boot. Managed hooks in each worktree curl events here; the STATUS MACHINE updates AGENT STATUS and broadcasts StatusChanged to all TUIs.
